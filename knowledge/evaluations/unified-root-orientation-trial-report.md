# Field report — Unified-root orientation trial

**Disposition:** do not implement an orientation-compiler kernel feature from
this run. The treatment reached the same correct conclusion while costing more,
although it opened fewer files and held a smaller peak context window. Preserve
the design hypothesis, simplify the recipe, and test again only on a task whose
public charter does not already contain an unusually complete implementation
log.

## 1. Trial and validity

The matched retry (`0822b369-7df9-49c7-b8ea-db7b8dd3802b`) used two fresh native
`scout` agents on the frozen refs predeclared in the
[protocol](unified-root-orientation-trial-protocol.md). The control was
prohibited from Agent Workspace. The treatment's first command was
`agent-workspace status --repository . --summary`, followed by the fixed
intent-relative recipe. Both stayed inside the platform repository, changed no
tracked file or durable project/workspace record, and ended with only the
pre-existing dirty `clearhead.nvim` marker.

The run is valid for comparing these two prompt/tool paths. It is not a test of
a future integrated `workspace_orient` verb: the treatment used the CLI through
a shell and spent calls discovering incorrect reveal/full syntax that an MCP
surface could avoid.

## 2. Outcome

Both arms independently concluded that:

- unified-root specifications, initialization, loading, doctor reconciliation,
  sentinel consolidation, and platform migration already landed;
- the parent and broad child actions still say not-started/migration-pending,
  contradicting the charter log, completed actions, Git history, tests, and
  migrated workspace state;
- canonical primitives already exist, including `ROOT_ANCHOR_STEM`,
  `PRIMARY_ACTIONS_FILE`, and `PRIMARY_DOCUMENT_FILE`;
- remaining technical gaps are LSP-level conformance and the separately
  unspecified migration from directory-derived root completed-history naming to
  `next.completed.actions`;
- the safest bounded technical change is LSP conformance coverage, while history
  naming needs specification first.

Both missed the strongest predeclared governance answer: neither made lifecycle
reconciliation or explicit owner confirmation a prerequisite before coding.
They recognized tracker lag and stopped without edits, so this was partial rather
than absent.

## 5. What the wake changed

The treatment wake immediately supplied the correct high-level frame: the goal
was unified-root closeout, the work shipped on 2026-09-15, and Agent Workspace
was coordination rather than product authority. That prevented an initial
“implement the action as written” interpretation.

However, the control obtained the same frame cheaply from the owning charter's
2026-09-15 log, which already names landed commits and residual gaps. Both agents
then verified the same specifications, source seams, tests, and Git history.
The wake reduced file breadth but did not change the final decision or catch a
failure the control missed.

Treatment friction included failed attempts to use MCP-style
`workspace_reveal` as a CLI subcommand and to combine summary/full status flags.
Those calls are workflow overhead, not evidence against provenance or freshness.
They do show that a future recipe must use the native surface actually available
rather than translate tool names across adapters.

## 6. Interpretation

This task has a ceiling effect: its charter is already a strong orientation
capsule. Clearhead plus a disciplined agent reconstructed the authority chain
without human recap and without Agent Workspace. Building a second capsule over
that would duplicate good public documentation.

The useful product boundary is narrower:

- keep the bounded wake for intent, continuity, and changed-support signals;
- let strong public charters/specifications carry accepted architecture and
  implementation history;
- improve relevance only when the public record does not already provide it;
- target future trials at capability reuse or cross-repository authority that
  cannot be recovered from one excellent charter;
- remove recipe ceremony before adding machinery.

One run, one task, and a low-thinking scout pair do not reject the orientation
compiler hypothesis generally. They reject implementation on the strength of
this candidate.
